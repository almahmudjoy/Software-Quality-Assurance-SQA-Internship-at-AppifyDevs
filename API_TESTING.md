# EchoGPT API Testing Report

## 1. Scope

The EchoGPT Chat API was tested with Postman against the chat-generation endpoint.

| Item | Detail |
|---|---|
| Endpoint | `https://api.echogpt.live/v1/chat/generate` |
| Method | `POST` |
| Content type | `application/json` |
| Authentication | Bearer token |
| Model tested | `zai-org/GLM-5.2` |
| Tool | Postman |
| Total scenarios | 10 |
| Positive scenarios | 1 |
| Negative/validation scenarios | 9 |

> Security note: the Postman collection in this repository has been sanitized. It contains `{{bearer_token}}` and `{{echoGPT_cookie}}` placeholders instead of credentials. Never commit a real token or cookie.

## 2. Request Contract

```json
{
  "messageId": "msg_1790434025307",
  "message": "what is 7+2?",
  "chatId": "9c3f8b06-d866-4ac0-9e03-c639dbbee978",
  "model": "zai-org/GLM-5.2",
  "stream": false
}
```

## 6. Common Error Response

API-002 through API-010 commonly returned:

```json
{
  "statusCode": 400,
  "success": false,
  "message": "Cannot read properties of null (reading 'quotaWindowStart')",
  "data": null
}
```

The HTTP status indicates rejection, but the message is not specific to the invalid field.

## 7. API Issues Identified

### BUG-API-001: Non-specific internal error for invalid requests

- Severity: Medium
- Priority: Medium
- Reproduction: send `POST /v1/chat/generate` with a required field removed, for example `message`.
- Expected: `400 Bad Request` with a useful message such as `message is required`.
- Actual: `400 Bad Request` with `Cannot read properties of null (reading 'quotaWindowStart')`.
- Impact: consumers cannot quickly identify how to correct the request.

### BUG-API-002: Same error for different validation failures

- Severity: Medium
- Priority: Medium
- Reproduction: repeat the request with an empty message, wrong message type, invalid/missing model, missing IDs, and invalid stream type.
- Expected: distinct validation feedback for each invalid parameter.
- Actual: materially different invalid requests return the same internal error.
- Impact: weakens API debugging and automated client-side error handling.

## 8. Limitations and Recommendation

The `stream:true` behavior was not conclusively evaluated because the request returned `400 Bad Request` and an account quota limitation (`429 Too Many Requests`) was also encountered during earlier testing. This result should not be treated as proof that streaming is broken.

Recommended improvements:

1. Validate request fields before quota/account lookup.
2. Return field-specific messages and a stable error code.
3. Avoid exposing internal JavaScript exception text to API consumers.
4. Document the streaming response format and test it with a fresh eligible account.
